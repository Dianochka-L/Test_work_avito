# Кандидатогенерация для поиска услуг Авито

Надо по запросу найти до 50 объявлений, среди которых окажется то, что выбрал пользователь. Метрика Recall@50.

На моей локальной валидации получилось примерно 0.95. На скрытой выборке 0.91 Для сравнения, обычный BM25 с фильтром по городу даёт 0.58, так что есть чем гордиться :)
Весов модели здесь не будет, так как в лимит гитхаба они не поместятся, зато код обучения описан здесь хорошо... Если всё же очень потребуется проверка с моими весами, свяжитесь со мной, попробую разделить и составить скрипт для склейки

## Про данные

Самое важное — локация. 83% выбранных объявлений лежат в той же локации, что и поиск. Но около 17% запросов бенчмарка сделаны по регионам (Москва с областью, СПб с областью, вся Россия), и у таких локаций своих объявлений нет вообще. Поэтому жёстко фильтровать по городу нельзя. Вместо этого я посчитала по train, в каких локациях выбирают объявления при поиске из данной локации, и использую это как мягкий приор. Плюс расстояние до центра локации.

Корпус похож на "релевантные + случайные объявления из тех же локаций"... число объявлений в локации почти идеально пропорционально числу запросов оттуда (корреляция 0.99). Получается, задача в том, чтобы найти нужное объявление среди нескольких тысяч в регионе.

Только 37% текстов запросов бенчмарка встречаются в train, и запросы там длиннее. Значит, просто запомнить пары "запрос - объявление" не выйдет, нужны модели, которые обобщают.

При этом 40% выбранных объявлений встречаются в train по другим запросам. Отсюда появилась "история" объявления — тексты запросов, по которым его выбирали. По сути бесплатное расширение документа...

## Как устроено

Для каждого запроса собираю кандидатов из нескольких источников:
- BM25 по стемам (заголовок, описание, параметры), стемминг через Snowball
- TF-IDF по символьным n-граммам, чтобы ловить опечатки и сокращения вроде "англ"
- BM25 и dense-сходство по истории объявления
- две dense-модели `intfloat/multilingual-e5-small` и `sergeyzh/rubert-tiny-turbo`, обе дообучены на парах запрос - объявление из train (InfoNCE, негативы из батча)
- классификатор "запрос - подкатегория" на TF-IDF

К каждому скору добавляется локационный приор. Топы всех источников объединяются, выходит около 500 кандидатов на запрос, и среди них оказывается 98.4% нужных объявлений.

Дальше LightGBM (lambdarank) выбирает 50. Признаки у него такие: скоры источников, их ранги и нормировки внутри запроса, доля слов запроса в заголовке, совпадение фильтров поиска с параметрами объявления, локация и расстояние, вероятность подкатегории, рейтинг, отзывы, цена, популярность объявления в train, длина запроса. Финальная модель — усреднение 5 бустингов с разными сидами.

## Как проверяла качество

Разметки у бенчмарка нет, поэтому пришлось собрать валидацию, максимально на него похожую (`src/make_split.py`):
- 6000 групп (запрос, локация, фильтры) из train, только из локаций бенчмарка 
- распределение длины запросов и доли пустых фильтров подогнано под бенчмарк 
- доля текстов, которые встречаются в оставшемся train, вышла 37%, как в бенчмарке, и это само сошлось, что приятно :)
- корпус = корпус бенчмарка + релевантные объявления валидации 
- валидация разбита на два фолда по 3000, каждому фолду видны только его релевантные, чтобы плотность была как в бенчмарке 
- строки валидации выкинуты из train, и все статистики и dense-модели учатся уже без них.

Ранжировщик учится на одном фолде и проверяется на другом, потом наоборот. Отдельно смотрела на "чистое" подмножество, где все релевантные объявления изначально лежат в корпусе бенчмарка, то есть ничего не подмешано. Там цифры примерно те же, значит валидация не врёт

Как рос скор: BM25 с жёстким фильтром 0.578, взвешенная сумма источников 0.882, плюс LightGBM 0.926, плюс дообученная e5 0.948, плюс вторая модель и ансамбль 0.951

## Ошибки, которые нашла

Утечка в валидации. Первый прогон дал подозрительные 0.94 ещё без dense-модели. Оказалось, что добавленные объявления валидации лежали в конце корпуса, а признак-ранг при равных значениях сортировался по индексу. Бустинг просто научился их узнавать. Починила перемешиванием корпуса, и честная цифра стала 0.926.

Жёсткий фильтр по локации. Он отрезал регионы и в Москве давал пул в десятки тысяч объявлений. Заменила на мягкий приор, и уже без dense-модели скор прыгнул с 0.58 почти до 0.9.

Семантические промахи вроде "перевозка мебели с грузчиками" - "Услуги грузчиков", где у запроса и объявления мало общих слов. Их закрыли дообученные dense-модели

Что осталось. Основная часть промахов — запросы, где в регионе десятки одинаковых по смыслу объявлений ("репетитор по английскому"), и пользователь выбрал одно из них почти случайно. Из текста это не вытащить, поэтому дальше я не копала. Попытки с третьей моделью, тюнингом бустинга и большим объёмом данных для ранжировщика давали прирост на уровне шума.

Ещё из технического... `deepvk/USER-base` на MPS обучался бы часов 5 и к тому же ушёл в NaN, так что от него отказалась... ничего не поделать

## Как запустить

```
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r requirements.txt
```

Данные из задания нужно положить в `dataset/`

Дальше просто `./run_all.sh`. Он соберёт валидацию, дообучит обе модели, построит признаки и запишет `answer.csv`. На M4 Pro это часа два было

Всё, кроме дообучения dense-моделей, детерминировано: я прогнала цепочку заново от сохранённых весов и получила побайтово тот же `answer.csv`, который отправила. А вот обучение на GPU Mac (MPS) даёт крошечные расхождения весов от запуска к запуску, я проверяла. Поэтому при обучении с нуля ответ будет очень близким, но не идентичным. Если лежат готовые веса в `work/dense_e5s` и `work/dense_tiny`, `run_all.sh` пропускает обучение и выдаёт ровно отправленный файл... как-то так :)

Оценка на валидации `.venv/bin/python src/evaluate.py work/val_feats.parquet`

## Файлы

- `src/make_split.py` — валидация
- `src/finetune_dense.py`, `src/dense_encode.py`, `src/dense_text.py` — dense-модели
- `src/textindex.py` — BM25 и символьный TF-IDF
- `src/pipeline.py` — локации, подкатегории, кандидаты и признаки
- `src/build_val.py`, `src/build_bench.py` — признаки для валидации и бенчмарка
- `src/ranker.py`, `src/evaluate.py` — бустинг и оценка
- `src/make_submission.py` — финальный `answer.csv`

Из open-source использовала numpy, pandas, scipy, scikit-learn, LightGBM, PyStemmer, PyTorch, transformers и две модели с HuggingFace. Всё работает локально, внешние API не нужны :)
